# じゃんかねの課題・仕様・レビューの扱い

## 課題と仕様の参照元

このプロジェクトのリポジトリは `70230kW/road-to-rich`。既存の GitHub Issues・Pull Requests と、リポジトリ内の設計資料を尊重する。

作業の要求仕様は、次の順で確認する。

1. 現在のユーザー依頼と、その作業について既に合意した内容。
2. ユーザーが指定した Issue・PR・仕様ファイル。
3. 変更対象に関係する `docs/design/` などの既存資料。古い案が残っている場合は、現在の実装と後続の決定を確認する。

新しい機能で仕様を記録する必要がある場合は、関連する既存資料を更新するか、`docs/design/` に目的の明確なファイルを追加する。既存の単純な修正に長い仕様書を必須にしない。仕様を記録することと、外部の課題管理サービスへ投稿することは別の操作として扱う。

## 外部の課題管理を変更する範囲

- GitHub の Issue・コメント・レビュー依頼などの作成、課題ラベルの追加・変更は、ユーザーがその操作を依頼した場合に行う。
- スキル導入や通常の実装修正を理由に、未依頼の Issue、外部コメント、トリアージラベルを作成しない。
- PR を作る依頼がある場合は、既存の `.github/pull_request_template.md` を使い、変更の目的・挙動・実際に行った確認を書く。
- `update-changelog.yml` と `scripts/update-changelog.mjs` による、マージ済み PR からのアプデ履歴生成を尊重する。開発スキルの導入だけを理由に、この自動化や既存ラベルを作り替えない。

## code-review を呼ぶときの入力

レビューを開始するときに、次の情報を一度確定して渡す。

1. **比較基準**：作業開始時に確認した `origin/main` のコミット SHA。`git rev-parse --verify origin/main` で得た値と、取得時点を作業メモに残す。ユーザーが別の比較対象を指定している場合はそれを優先する。
2. **要求仕様**：該当する仕様ファイルのパスと、現在の依頼に含まれる受け入れ条件。Issue を指定された場合は、取得した本文も渡す。
3. **開発ルール**：ルート `AGENTS.md`、該当する設計資料、変更対象に適用される規約。
4. **確認結果**：実行したコマンドと結果、ブラウザーで確認した範囲、未確認の点。

呼び出し例：

```text
code-review を使って、比較基準 <作業開始時に取得した origin/main の SHA> から
現在の HEAD までをレビューしてください。
仕様は docs/design/<今回の仕様>.md と、今回のユーザー依頼です。
AGENTS.md と関連する設計資料を規約として確認してください。
仕様適合とコード品質を分けて報告し、外部への投稿は行わないでください。
```

比較基準の SHA が解決できることと、対象差分が存在することを先に確認する。作業中の未コミット変更もレビュー対象なら、`git diff` と `git diff --cached` の差分を明示的に追加する。`git diff <基準SHA>...HEAD` だけでは未コミット変更を確認できない。

独立した仕様ファイルがない小さな修正では、現在のユーザー依頼を要求仕様としてレビューへ渡す。確認できない仕様を推測して作ったり、仕様ファイルがないことだけで通常のレビューを停止したりしない。仕様そのものが不明な箇所は、未確認事項として区別する。

## Matt Pocock スキルの設定について

このファイルとルートの開発ルールが、導入済み `code-review` に必要な課題管理先・仕様参照元を提供する。これらが読める場合、`setup-matt-pocock-skills` の追加導入・再実行は不要。

全パックに含まれる `triage`、`to-spec`、`to-tickets` などは、この導入の前提にしない。未導入スキルを呼ぶために作業を止めたり、別の課題管理方式へ切り替えたりしない。
